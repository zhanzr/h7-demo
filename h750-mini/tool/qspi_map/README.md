# qspi_map

Two-stage firmware that boots the STM32H750 from internal flash and runs the
main app **entirely from the QSPI-mapped space** (W25Q64 memory-mapped at
0x90000000). The bootloader initializes the QUADSPI + flash, and if the flash
does not already contain the app (or the embedded image is newer) it programs
the app into the W25Q64 itself using the same driver as the benchmark, then
jumps.

```
+--------------------------------------------------------------+
| stage 1 (internal flash 0x08000000): bootloader              |
|   - 480 MHz clock tree, USART1 console, LED                  |
|   - QUADSPI init (PLL2 -> 100 MHz, QE set)                   |
|   - if app missing/outdated: program embedded app into W25Q64|
|   - QUADSPI -> memory-mapped mode (0xEB 1-4-4)               |
|   - set VTOR = 0x90000000, MSP, jump to app reset vector     |
+--------------------------------------------------------------+
                             |  (jump, no reset)
                             v
+--------------------------------------------------------------+
| stage 2 (QSPI space 0x90000000): app                         |
|   - linked at 0x90000000 (app.ld, vector table first)        |
|   - SystemInit that does NOT touch RCC/PLL2 (bootloader owns)|
|   - __enable_irq() (jump leaves PRIMASK set)                 |
|   - blink LED + "running from QSPI flash"                    |
+--------------------------------------------------------------+
```

## Build

```
bash build.sh                          # builds boot.elf/.hex and app.elf/.hex/.bin
ninja flash                            # flash bootloader to internal flash (probe-rs)
```

Notes:

- `-DBOOT_FLASH_2M=ON` links the bootloader against 2 Mbyte internal flash
  (shadow STM32H743VI part) instead of 128 Kbyte.
- The bootloader embeds the app image (`boot/src/app_image.c`, regenerated from
  `app.bin` after app changes) and programs it into the W25Q64 at first boot /
  whenever the content differs. So a single `ninja flash` + power-on gives a
  working system.
- The app must NOT reconfigure the system clocks or the QUADSPI - its own code
  lives there. It only re-inits USART1 + LED and re-enables interrupts.

## Measured results

- **Boot + jump + app running from QSPI**: works (console shows the bootloader
  banner, then `=== qspi_map app: RUNNING FROM QSPI FLASH @ 0x90000000 ===`
  and the LED loop).
- Flash speed (W25Q64, via the firmware driver, 100 MHz QSPI, 1-1-4 program):
  - 64K block erase ~190 ms, 4K sector ~53 ms
  - page program ~562-569 KiB/s
  - memory-mapped read 1-4-4 ~47.7 MiB/s (see spi_flash_test/README.md)

## Flashing benchmarks (this board, ULINK2/CMSIS-DAP)

### Internal flash (bootloader, 97 KB)

| tool    | time   | notes |
|---------|--------|-------|
| openocd | 3.59 s | `openocd -f tools/openocd_ulink2.cfg -c "program boot.hex verify reset exit"` |
| probe-rs| 19.56 s| `probe-rs download --chip STM32H750VB ... boot.hex` |

### External QSPI flash (the app at 0x90000000)

- **openocd (stmqspi driver): attempted, NOT working on this part.** The
  driver and bank config load fine (see `tools/openocd_qspi_h750.cfg`), but the
  write-enable command never latches (`Cannot write enable flash1. Status=0x00`)
  and memory-mapped reads return 0. Root causes found while debugging the H750
  QUADSPI **v2** register layout (all now fixed in the config, but the flash op
  still does not complete):
  - `FMODE` lives in the **CCR** (bits 27:26), not the CR.
  - `DCR.FSIZE` is at bits 20:16, `CR.PRESCALER` at bits 31:24.
  - `D1CCIPR.QSPISEL` is 00=D1HCLK, 01=PLL1_Q, **10=PLL2_R**, 11=CLKP (not HSI).
  - the stmqspi driver derives the indirect command line-modes from the memmap
    CCR, so the memmap read must be 1-line (0x03), not 0xEB.
  - a bogus clock config while the CPU is halted can wedge the AHB-AP
    (recovered with `probe-rs download --connect-under-reset`).
  Conclusion: the register-level QUADSPI init from a *halted* CPU (openocd's
  model) is fragile here; the working QSPI path is code running on the CPU (the
  firmware driver), which is exactly what a probe-rs/Keil flash algorithm does.
- **probe-rs: custom W25Q64 flash algorithm WORKS - via a plain bit-banged SPI
  on the QUADSPI pins.** A fully position-independent CMSIS-style algorithm was
  written in C (`algo/flash_w25q64.c`) and wired up via a custom target YAML
  (`algo/target_w25q64.yaml`, generated by `algo/build_algo.py`). probe-rs loads
  and runs it correctly (Init/EraseSector/ProgramPage are all called), and the
  W25Q64 **is programmed**: `probe-rs download --chip-description-path
  target_w25q64.yaml --chip STM32H750VB-W25Q64 ... app.hex` (without --verify)
  completes in ~26 s and the bootloader then boots the app from the flash.
  - The earlier QUADSPI-peripheral approach failed because the H750 QUADSPI
    needs a PLL2 kernel clock that cannot be brought up from the algorithm's
    execution context (chip at reset/HSI): even with the LDO/VOS power config
    applied first, PLL2RDY never sets, and D1HCLK (QSPISEL=0) does not drive the
    flash either. HSE/HSI are not direct QSPI kernel options. The only reliable
    QSPI clock is the one the firmware brings up at boot (PLL2 via the full HAL
    sequence). This is the same class of blocker as the openocd attempt.
  - So the algorithm bit-bangs the W25Q64's 1-line SPI commands on the QUADSPI
    pins as plain GPIOs: SCK=PB2, CS=PB6, MOSI/DI=PD11, MISO/DO=PD12, with
    /WP=PE2 and /HOLD=PD13 driven high. No PLL and no QUADSPI peripheral are
    used. 0x02 page-program / 0x20 sector-erase / 0x05 status all work; the
    erase+program result is byte-perfect (verified against app.bin - the only
    difference is the 0x28-byte linker gap at 0x90000298, which is 0xFF erased
    in flash but 0x00 in app.bin; the bootloader's checksum ignores such gap
    bytes and the app runs fine).
  - `Init` sends a 0xF0 reset first, and the algorithm sends it before **every**
    read transaction (the running app leaves the flash in continuous-read mode
    from memmap reads; that state survives CPU resets and garbles reads, which
    is what made a 64 KB image look "corrupted" at high offsets).
  - The algorithm is **self-verifying**: it read-back-verifies every 256-byte
    page program and every 4 KB sector erase (in 8-byte chunks, each with a
    fresh 0xF0 reset) and retries on mismatch. This replaces the need for
    `--verify` (probe-rs's own external verify path was unreliable). Verified
    byte-perfect for images from 41 KB (`app`) to 64 KB (`coremark_480m`).

### Notes / status

- The algorithm mechanism and build tooling work end-to-end (probe-rs loads the
  position-independent ELF blob and calls the entry points). See
  `algo/flash_w25q64.c`, `algo/flash_w25q64_fast.c`,
  `algo/flash_w25q64_qspi.c`, and `algo/build_algo.py`.
- **`flash_w25q64_qspi.c` (the hardware-QUADSPI algorithm) is now the
  recommended driver** (~5 s for 41 KB vs ~6 s fast bit-bang vs ~14 s basic;
  the old ~16-44 s figures were dominated by probe-rs's 256-byte `page_size`,
  not SPI). It was debugged to completion with the `qspi_alg_test` harness.
  Two discoveries made it work on HSI with **no PLL at all**:
  1. The QUADSPI's **NCS (PB6) is high-impedance when idle** and PB6 has an
     external pull-down on this board → the flash stayed permanently selected
     and entered continuous-read mode after the first command. **CS is driven
     manually as a GPIO output** around each transfer.
  2. The **DR FIFO must be read/written as 32-bit words** (byte accesses do not
     pop/push the FIFO - every byte read returns the same oldest byte).
- Earlier PLL2 findings (PLLSRC=HSE, DIVM2=25, N2=400, LDO/VOS) are
  documented in git history but no longer needed for the QUADSPI algorithm.
- H750 QUADSPI v2 register layout (for reference): FMODE in CCR bits 27:26,
  FSIZE in DCR bits 20:16, PRESCALER in CR bits 31:24, SSHIFT in CR bit 4.

Build: `python algo/build_algo.py flash_w25q64_qspi.c 0x4000` -> regenerates
`algo/target_w25q64_qspi.yaml` (the optional 2nd arg is the probe-rs
`page_size`; requires arm-none-eabi-gcc; the blob is extracted from the linked
ELF at 0x20000000 with the entry-point offsets computed by `nm`).

### Working probe-rs external QSPI flash command (QUADSPI algorithm)

```
probe-rs download --probe c251:2722:V0010M9E \
  --chip-description-path algo/target_w25q64_qspi.yaml \
  --chip STM32H750VB-W25Q64-w25q64_qspi --protocol swd \
  --binary-format hex --non-interactive --disable-progressbars \
  build/app.hex
```

Measured on the 41 KB app (erase 11x4 K + ~160 page programs via the bit-bang
GPIO SPI at HSI 64 MHz): **~26.5 s**, then a reset boots the app from the flash.
For comparison: internal flash via openocd = 3.59 s, via probe-rs = 19.56 s.
Use without `--verify` (see the read-back limitation above).

## Flashing the app without openocd/probe-rs external support

The bootloader self-programs the embedded app into the W25Q64 on first boot /
when the content differs. To re-flash a new app, rebuild + regenerate
`app_image.c` (a `ninja app_bin` + the generator script, see `build.sh`) and
re-flash the bootloader - the next boot updates the QSPI flash.

## Is probe-rs's flash algorithm the same as Keil MDK's .FLM?

**Yes - both use the CMSIS flash-algorithm (.FLM) format.** A Keil `.FLM` is an
ELF exposing `Init`/`Uninit`/`EraseChip`/`EraseSector`/`ProgramPage`/`Verify`
plus a device descriptor; probe-rs's flash algorithms implement the same API and
probe-rs's `target-gen` tool can convert a Keil `.FLM` into a probe-rs target
YAML. So a `.FLM` written for Keil can be reused by probe-rs (and vice versa),
as long as it targets the same MCU/peripheral. What is NOT compatible:
STM32CubeProgrammer's `.stldr` external loaders (ST-proprietary format) and
probe-rs's own `flash-algorithm`-crate output (probe-rs-specific, though also
ELF).

## Directory layout

```
boot/          stage-1 bootloader (internal flash)
  src/main.c       init, QSPI, self-program, jump
  src/app_image.c  embedded app image (generated)
  boot.ld / boot_2m.ld
bare/           stage-2 app (QSPI space)
  src/main.c       blink + "running from QSPI flash"
  src/system_app.c non-destructive SystemInit (bootloader owns RCC/PLL2)
  app.ld           code at 0x90000000
tools/openocd_qspi_h750.cfg   openocd stmqspi config (external QSPI)
```
